# T1033 — System Owner/User Discovery

## Summary

Rejewski emulates an adversary establishing *who* they are and *who owns the tenant* — the
first orientation an attacker performs after gaining access. Two existing surfaces cover it.
**Surface A — operator identity resolution**: which account has been compromised (UPN, object
ID, home tenant). **Surface B — tenant owner/admin identification**: who administers the tenant
(Global Administrator, Privileged Role Administrator, and other owner-class role holders). In
the cloud-identity setting, "system owner/user" is the tenant's users and its administrators;
answering both questions is prerequisite to selecting escalation and impersonation targets.

## ATT&CK reference

<https://attack.mitre.org/techniques/T1033/>

## Borrowed client

Microsoft Graph Command Line Tools (14d82eec-204b-4c2f-b7e8-296a70dab67e). The FOCI client is
fixed to 14d82eec per ADR 0006 and guardrail G-3; no tenant-side application registration is
created (ADR 0001 §1, threat-model.md §3).

## Procedure

### Surface A — Operator identity resolution

1. `scripts/identity.py` acquires (or silently reuses) a delegated Graph token for the operator
   account. The operator's identity — UPN, and home tenant — is established through the
   authenticated context (`actor_upn`, the token's home-tenant binding, and the returned
   `correlation_id`); identity.py does **not** itself issue `GET /me`.
2. The `GET /me` profile read that confirms owner identity (id, displayName, userPrincipalName)
   is performed by `scripts/step4-token-smoke.py` as the T1078.004 valid-account confirmation
   step. That read is the explicit "who is this account" answer; identity.py provides the
   authenticated identity context it runs under.

### Surface B — Tenant owner/admin identification

3. `scripts/tool_list_role_assignments.py` (already implemented for T1087.004 Surface C) issues
   `GET /roleManagement/directory/roleAssignments` (with the two-call `$expand=principal` /
   `$expand=roleDefinition` merge, per B030) to enumerate directory role assignments, resolving
   which principals hold Global Administrator, Privileged Role Administrator, and other
   owner-class roles — i.e., who owns/administers the tenant.
4. A `graph_call` replay-log entry is written per G-5 for each Graph read.

## Guardrails

- G-1 (sandbox tenant only, read-only): all Graph calls target cloudharbordemo
  76b87c33-6178-4ff9-94a7-164792c8e4c6; GET only.
- G-3 (borrowed client / read-only scope): Surface A resolves identity as a side-effect of token
  acquisition (any scope); Surface B requires RoleManagement.Read.Directory on the borrowed
  client 14d82eec and Directory Readers on the signed-in account.
- G-6 (data redaction): the sandbox tenant GUID is redacted from tool evidence output; operator
  UPN/object IDs are sandbox values (cloudharbor-demo.com).

## Detection signals

- **MicrosoftGraphActivityLogs:** `GET /me` and `GET /roleManagement/directory/roleAssignments`
  from the FOCI client ID (14d82eec). A member account enumerating directory role assignments is
  a strong owner-discovery indicator.
- **Entra ID sign-in logs:** the identity-resolution and role reads correlate to the T1078.004
  session correlation ID.

## Evidence

- **Surface A — R011 (2026-07-18).** The R011 sweep contains successful T1550.001 `token_event`
  entries from `scripts/identity.py`, establishing the operator identity context
  (meganb@cloudharbor-demo.com, cloudharbordemo). The standalone `GET /me` profile read
  (step4-token-smoke.py) is documented under T1078.004; a T1078.004 replay sample captures it.
- **Surface B — pending a post-B030 run.** In R011, `tool_list_role_assignments.py` returned
  HTTP 400 ("Only one property can be expanded in a single query" — the B030 defect, fixed in
  PR #71), so R011 holds an *error* entry for that call, not a successful enumeration. Successful
  Surface B evidence will be captured on the next consented run against cloudharbordemo now that
  B030 is merged.

## Limitations

- `scripts/identity.py` does not issue a standalone `GET /me`; operator identity is resolved from
  the authenticated token context, and the explicit profile read lives in step4-token-smoke.py
  (the T1078.004 confirmation surface). Surface A is therefore identity *resolution*, not a
  dedicated user-directory read.
- Surface B enumerates directory role assignments; it does not resolve nested group-based role
  eligibility or PIM-eligible (not-yet-activated) assignments, which are deferred surfaces.
