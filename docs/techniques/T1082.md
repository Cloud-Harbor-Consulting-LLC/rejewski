# T1082 — System Information Discovery

## Summary

Rejewski emulates an adversary who enumerates the Intune managed-device inventory via
Microsoft Graph GET /deviceManagement/managedDevices. The managed-device collection is a
system-information goldmine: per device it yields the device name, owner type (company vs
personal), operating system and version, compliance state, management state, enrollment and
last-sync timestamps, the bound Entra device ID, the assigned user (UPN and display name),
hardware manufacturer and model, and disk-encryption status. From this one paged read an
adversary maps the endpoint estate — which OS versions are in play (and therefore which
client-side exploits apply), which devices are non-compliant or unencrypted (softer targets),
which hardware models are deployed, and which users own which devices (pivot and targeting
data). This is system-information discovery at fleet scale, the cloud-managed analogue of an
on-host `systeminfo` sweep.

Non-compliant and unencrypted devices are of particular adversary interest: they indicate
endpoints outside the protection of Conditional Access compliance grants (enumerable via
Tool 4 / T1526) and represent the path of least resistance for client-side compromise.

Note: GET /organization (the tenant top-level configuration object — hybrid-sync state,
verified domains, provisioned plans, notification contacts) was the originally catalogued
candidate for this technique and remains a valid, complementary T1082 surface: it answers
"what is the tenant", whereas the implemented managed-device surface answers "what are the
endpoints". The /organization surface is deferred to a later Rejewski tool. This module
governs the implemented Intune managed-device surface.

## Borrowed client

Microsoft Graph Command Line Tools (14d82eec-204b-4c2f-b7e8-296a70dab67e). Inherits the
borrowed-client decision from T1078.004; no separate client acquisition occurs.
No tenant-side application registration is created. The no-tenant-app-reg posture
(ADR 0001 §1, threat-model.md §3) is maintained throughout.

## Required privilege

GET /deviceManagement/managedDevices requires the `DeviceManagementManagedDevices.Read.All`
delegated scope, admin-consented on the borrowed Microsoft Graph Command Line Tools FOCI
client in the lab tenant. Managed-device enumeration is gated behind an
Intune-administrator-class grant; like CA-policy (T1526) and DfI-sensor (T1518.001)
enumeration, it is a **post-foothold** discovery step rather than a first-foothold
capability. In the lab tenant, meganb@<lab-domain> holds the requisite
grant to simulate that scenario.

## Procedure

1. Operator confirms a valid Graph token from T1078.004 is in scope. The token is acquired
   and silently reused through scripts/identity.py (ADR 0005 encrypted cache).
2. Operator runs `scripts/tool_intune_devices.py`, which calls
   GET /deviceManagement/managedDevices with a `$select` restricting the projection to the
   documented surface and `$top=100`, then follows `@odata.nextLink` until the inventory is
   exhausted. Unlike the directory endpoints, the Intune device inventory routinely spans
   multiple pages, so pagination runs on every real invocation.
3. The `$select` projection captures:
   `id`, `deviceName`, `managedDeviceOwnerType`, `operatingSystem`, `osVersion`,
   `complianceState`, `managementState`, `lastSyncDateTime`, `enrolledDateTime`,
   `azureADDeviceId`, `userPrincipalName`, `userDisplayName`, `manufacturer`, `model`,
   `isEncrypted`.
   - `complianceState`: compliant | noncompliant | unknown | conflict | error |
     inGracePeriod | configManager
4. The tool computes an aggregate summary into the evidence JSON: total device count,
   compliant vs non-compliant counts, encrypted vs not-encrypted counts, and per-field
   breakdowns (compliance state, owner type, operating system). These are the
   detection-engineering and targeting payload of the run.
5. An empty inventory is handled gracefully — the tool prints "No managed devices found" to
   stderr and still records a graph_call replay-log entry with `row_count` (object_count) 0.
   It is never treated as an error.
6. Every emitted invocation writes a replay-log entry (kind=graph_call) per G-5, recording
   the `/deviceManagement/managedDevices` endpoint, GET method, HTTP status, and the total
   device count across all pages.

## Guardrails

- G-1 (consent-bound tenant lock, ADR 0008): all Graph calls target the one tenant named in the run's consent record; the evidence in this repo comes from the lab tenant.
- G-3 (read-only scope): GET only; no device configuration, wipe, or management writes.
- G-6 (audit-log redaction): no signed PDFs, tokens, or operator filesystem paths reach any
  committed file; the token_event cache_path is redacted to "<redacted>" by
  scripts/consolidate_run.py before a run sample lands under samples/. Device userPrincipalName
  and userDisplayName are sandbox values (<lab-domain>); they are retained in the
  evidence JSON for analysis but reviewed before any public-repo sample commit.
- G-7 (sandbox-only, no real production tenant): device inventory is read from the
  lab tenant only; all device and user identifiers are sandbox values.

## Detection signals

- MicrosoftGraphActivityLogs captures the GET /deviceManagement/managedDevices call from the
  FOCI client ID (14d82eec), including the RequestUri (with the `$select` projection) and the
  signing-in identity. A full managed-device read from a non-Intune-admin account is a strong
  bulk-enumeration indicator.
- Entra ID sign-in logs: correlatable via the T1078.004 session correlation ID.
- Microsoft Defender for Cloud Apps / XDR: a paged managedDevices enumeration produces a
  burst of Graph reads that is a consistent leading indicator of systematic tenant
  enumeration when chained with T1087.004, T1069.003, T1526, and T1518.001 calls in the same
  session.

## Evidence

- samples/replay-log/R008.json — consented run R008 (the lab tenant, 2026-06-16): graph_call
  entry for tool_intune_devices, GET /deviceManagement/managedDevices, 1 managed device
  enumerated, 1 page, outcome success. (Same run also carries the T1518.001 DfI-sensor
  graph_call entry and the two T1550.001 token_event entries.)

## Limitations

- GET /deviceManagement/managedDevices returns Intune-managed devices only. Devices that are
  Entra-registered/joined but not Intune-enrolled do not appear here; that surface is GET
  /devices (a directory-object enumeration, distinct from this MDM surface).
- `complianceState` reflects the last evaluation, not the live device state; a device that
  has not synced recently (`lastSyncDateTime`) may report stale compliance.
- The tenant top-level configuration (hybrid-sync state, verified domains, provisioned plans)
  is not part of this surface; that is the deferred GET /organization surface (see Summary
  note), which overlaps with the verifiedDomains data also reachable via T1482 (GET /domains).
