# T1087.003 — Account Discovery: Email Account

## Summary

Rejewski will emulate an adversary who, having enumerated user accounts via T1087.004,
extends discovery to the email identity surface: which accounts have Exchange Online
mailboxes, which are mail-enabled, which have proxy addresses or aliases, and whether
any shared or resource mailboxes exist. This intelligence is directly useful for
phishing-target selection, business email compromise (BEC) pre-positioning, and
identifying distribution lists that reach wide audiences inside the tenant. The technique
uses the same Graph /users endpoint as T1087.004 but with a distinct $select projection
targeting mail-specific attributes (mail, mailEnabled, proxyAddresses, mailNickname),
and may be extended to enumerate shared and room/equipment mailboxes via the Exchange
Online-specific resourceBehaviorOptions and userType attributes.

## Borrowed client

Microsoft Graph Command Line Tools (14d82eec-204b-4c2f-b7e8-296a70dab67e). Inherits the
borrowed-client decision from T1078.004; no separate client acquisition occurs.
No tenant-side application registration is created. The no-tenant-app-reg posture
(ADR 0001 §1, threat-model.md §3) is maintained throughout.

The Graph scopes required for this technique (User.Read.All) are a subset of those
already consented for T1087.004. No scope uplift is needed for the core email
enumeration surface.

## Required privilege

Any ordinary licensed user with User.Read.All granted via the FOCI client can call
GET /users with mail-attribute projections. No directory role is required. This keeps
T1087.003 at the same privilege tier as T1087.004, making it runnable immediately after
the T1078.004 initial-access step.

## Procedure

*Implementation pending Sprint 2. The procedure below defines the expected implementation
shape; it will be updated to reflect the actual script behaviour when Sprint 2 opens.*

1. Operator confirms a valid Graph token from T1078.004 is in scope.
2. Operator calls GET /users with $select=mail,mailEnabled,proxyAddresses,mailNickname,
   userType,displayName,id and pages through the full directory until exhausted or the
   G-9 row cap is hit.
3. Operator filters the result set to identify:
   - Accounts with a non-null `mail` field (Exchange Online mailboxes active).
   - Accounts with `mailEnabled: true` that lack a primary mailbox (mail-enabled security
     groups or distribution list members may appear here).
   - Accounts with multiple entries in `proxyAddresses` (aliases — useful for BEC
     address-collection).
   - Accounts with `userType: Guest` and a non-null `mail` (external collaborators with
     mailbox access to tenant resources).
4. Operator records account count, mailbox-enabled count, alias count, and guest-with-mail
   count into the run evidence ledger.
5. A replay-log entry (kind=graph_call) is written per G-5 requirements.

## Guardrails

- G-1 (consent-bound tenant lock, ADR 0008): all Graph calls target the one tenant named in the run's consent record; the evidence in this repo comes from the cloudharbordemo sandbox (76b87c33-6178-4ff9-94a7-164792c8e4c6).
- G-3 (read-only scope): GET only; no Mail.Send, no mailbox write operations.
- G-5 (evidence capture): replay-log entry written per run; aggregate counts in evidence JSON.
- G-6 (audit log redaction): email addresses are hashed in evidence files before any content
  reaches the public-repo samples/ directory; raw addresses remain in the operator-side
  SharePoint Evidence folder only.
- G-7 (no real user data): only seeded sandbox test accounts are targeted.
- G-9 (row cap): enumeration capped at DEFAULT_ROW_CAP (default 1 000 accounts).

## Detection signals

- Graph unified audit log: bulk /users enumeration from the FOCI client ID (14d82eec)
  with $select targeting mail attributes. This is the same call shape as T1087.004 Surface A
  but with a distinct $select projection; defenders correlating by $select contents can
  distinguish email-focused enumeration from generic account discovery.
- Entra ID sign-in logs: correlatable via the T1078.004 session correlation ID.
- Microsoft Defender for Cloud Apps: bulk user attribute read may surface as anomalous
  data access if MDCA has a baseline for the operator account type.
- Entra ID Identity Protection: same signals as T1087.004 — bulk API reads from a FOCI
  client following initial authentication.

## Limitations

- Shared and resource mailboxes (room, equipment) require a separate GET /users filter
  (`userType eq 'Guest'` does not surface all shared mailboxes). Full shared-mailbox
  enumeration via the Exchange Online-specific endpoint (GET /users?$filter=...) is
  deferred to the Sprint 2 implementation pass.
- Distribution lists and Microsoft 365 Groups with mail-enabled behaviour surface via
  T1069.003 (group discovery) rather than this module; this module covers user-object
  email attributes only.
- Mail.Read scope (to read mailbox content) is not required for email address enumeration
  and is explicitly excluded per G-3. This module covers identity-level email metadata,
  not mailbox content access.
- Guest accounts (userType: Guest) with external email addresses may appear in the result
  but reveal the tenant's external collaboration posture rather than internal targets.
  This is noted in the evidence ledger as a secondary finding.
