# T1087.004 — Account Discovery: Cloud Account

## Summary

Rejewski emulates an adversary who, having authenticated via T1078.004, enumerates user accounts in the target tenant via Microsoft Graph. Account discovery establishes the directory landscape — caller identity, peer accounts, and the caller's own group affiliations — that informs subsequent privilege-escalation and lateral-movement targeting. This module is read-only and stays within the consent floor declared in ADR 0001 §2.

## ATT&CK reference

<https://attack.mitre.org/techniques/T1087/004/>

## Borrowed client

Microsoft Graph Command Line Tools (14d82eec-204b-4c2f-b7e8-296a70dab67e). Inherits the borrowed-client decision from T1078.004; no separate client acquisition occurs.

## Procedure

### Surface A — User account enumeration (Tool 1, scripts/tool_list_users.py)

1. Operator confirms a valid Graph token from T1078.004 is in scope.
2. Operator calls GET /me to capture caller identity (UPN, object ID, displayName).
3. Operator calls GET /users to enumerate directory accounts; results paged at default 100/page until the directory is exhausted or the configured row cap is hit.
4. Operator calls GET /me/memberOf to enumerate the caller's direct group memberships (used as input to T1069.003).
5. Operator records each response correlation ID, page count, and account count into the run evidence ledger.

### Surface B — Application registration enumeration (Tool 3, scripts/tool_list_applications.py)

1. Operator calls GET /applications to enumerate tenant app registrations visible to the signed-in user.
2. Results paged at $top=999 until exhausted or row cap hit.

### Surface C — Directory role assignment enumeration (Tool 5, scripts/tool_list_role_assignments.py)

Requires Directory Readers role (minimum) on the signed-in user for complete tenant-wide
visibility. Security Reader gives partial visibility of security-relevant assignments only.

1. Operator confirms the signed-in account holds at least Directory Readers (or Security Reader
   for a partial enumeration acceptable to the simulation objective).
2. Operator calls GET /roleManagement/directory/roleAssignments with
   $expand=principal,roleDefinition to resolve display names inline.
3. Results paged at $top=100 until exhausted or row cap hit.
4. Tool computes aggregate metrics: Global Administrator count, high-privilege role count,
   external (guest) principal count, tenant-wide vs. AU-scoped assignment breakdown,
   unique principal count, and unique role count.
5. Evidence JSON (assignment records + aggregate metrics) written to stdout or --output.

### Surface D — Service principal enumeration (Tool 6, scripts/tool_list_service_principals.py)

Requires Directory Readers role (minimum) on the signed-in user for tenant-wide SP
visibility. Without this role, the endpoint returns an empty result set (HTTP 200,
`value: []`) rather than a 403 — the tool will complete with `row_count: 0`.

1. Operator confirms the signed-in account holds at least Directory Readers (or a higher
   role such as Global Reader or Application Administrator).
2. Operator calls GET /servicePrincipals with
   $select=id,appId,displayName,accountEnabled,servicePrincipalType,signInAudience,
   appOwnerOrganizationId,tags,homepage and $top=100 (the Graph endpoint maximum for
   this resource — distinct from /users which accepts $top=999).
3. Results paged at $top=100 until exhausted or row cap hit.
4. Tool computes aggregate metrics: enabled/disabled SP count, servicePrincipalType
   breakdown (Application / ManagedIdentity / Legacy / SocialIdp), multi-tenant SP count
   (signInAudience ≠ AzureADMyOrg), cross-tenant owner count (appOwnerOrganizationId from
   external tenants), and unique homepage count.
5. Evidence JSON (SP records + aggregate metrics) written to stdout or --output.

### Surface E — OAuth2 delegated permission grant enumeration (Tool 11, scripts/tool_list_oauth_grants.py)

Requires Directory Readers role (minimum) on the signed-in user. Directory.Read.All
scope must be admin-consented on the FOCI client in the target tenant.

1. Operator confirms the signed-in account holds at least Directory Readers.
2. Operator calls GET /oauth2PermissionGrants with
   $select=id,clientId,resourceId,consentType,principalId,scope and
   $top=100 pagination.
3. Results paged until exhausted or row cap hit.
4. Tool computes aggregate metrics: admin-consented grant count, user-consented grant
   count, unique client SP count, unique resource SP count, and high-privilege grant
   count (grants whose scope string contains a high-privilege API permission).
5. Evidence JSON (grant records + aggregate metrics) written to stdout or --output.

## Guardrails

- G-1 (sandbox tenant only): all Graph calls target cloudharbordemo 76b87c33-6178-4ff9-94a7-164792c8e4c6.
- G-3 (consent floor): only User.Read and User.ReadBasic.All scopes; no Directory.Read.All in Sprint 1 (deferred to Sprint 2 uplift).
- G-5 (evidence capture): full response correlation IDs and aggregate counts logged; raw response bodies redacted per G-6.
- G-6 (audit log redaction): account UPNs, emails, and object IDs are hashed in evidence files; the unredacted index lives in the SharePoint Evidence folder with restricted access.
- G-7 (no real user data): only seeded test accounts populate the sandbox tenant.

## Detection signals

- Graph audit log entries: bulk /users enumeration calls from the FOCI client ID.
- Entra ID directory audit: account-read activity correlated to the T1078.004 sign-in session.
- Anomalous enumeration volume signals (when defender baselines are configured) may surface in Microsoft Defender for Identity or Entra ID Identity Protection.
- GET /servicePrincipals bulk queries appear in MicrosoftGraphActivityLogs (when enabled) with the borrowed client ID (14d82eec), delegated token, and endpoint path.
- Microsoft Defender for Cloud Apps anomaly rules may fire if the enumeration session is followed by SP credential manipulation (e.g., "Unusual addition of credentials to an OAuth app").

## Limitations

- User enumeration (Surface A) caps at the configured row limit (default 1 000 accounts via G-9).
- Application registration enumeration (Surface B) covers app registrations only; service principal enumeration is implemented as Surface D (Tool 6, GET /servicePrincipals).
- Role assignment enumeration (Surface C) via Directory Readers gives complete tenant-wide visibility. Security Reader returns only security-relevant assignments; the exact subset is undocumented by Microsoft and must be validated empirically per tenant.
- Cross-tenant guest accounts are enumerated in the standard /users response but are not flagged separately in Surface A. Surface C does flag external (guest) principals in role assignments via the ra_external_principal_count evidence field.
- Delegated-grant enumeration (Surface E) covers OAuth2 delegated permission grants (GET /oauth2PermissionGrants) only. Application role assignments — the application-permission counterpart, exposed as appRoleAssignments on each service principal (GET /servicePrincipals/{id}/appRoleAssignments) — are a deferred surface not yet enumerated by Rejewski. Surface E therefore surfaces delegated (on-behalf-of-user) authorizations but not app-only (application-permission) authorizations.
