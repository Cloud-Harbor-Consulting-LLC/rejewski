# T1114.002 — Email Collection: Remote Email Collection

## Summary

Rejewski will emulate an adversary who collects email remotely through Microsoft Graph —
enumerating a target user's mail folders and listing message metadata without touching the
mailbox interactively. Where T1087.003 (Email Account discovery) identifies *which* mailboxes
exist, T1114.002 reaches into a mailbox to inventory its folders and messages.
GET /users/{user-id}/mailFolders enumerates the folder structure for a target user;
GET /users/{user-id}/messages with a metadata-only `$select` projection lists recent
messages (subject, from, receivedDateTime, hasAttachments — no body content in this step);
and GET /users/{user-id}/mailFolders/{folder-id}/messages lists messages within a specific
folder. The result is a remote inventory of a mailbox's structure and recent traffic —
the precursor to targeted message-content collection.

This technique is catalogued in the Collection tactic. Rejewski's read-only posture and
G-7 bound this module to metadata-level enumeration; message body content is not read in
the catalogued procedure.

## Borrowed client

Microsoft Graph Command Line Tools (14d82eec-204b-4c2f-b7e8-296a70dab67e). Inherits the
borrowed-client decision from T1078.004; no separate client acquisition occurs.
No tenant-side application registration is created. The no-tenant-app-reg posture
(ADR 0001 §1, threat-model.md §3) is maintained throughout.

This module documents **two distinct permission postures** with different reach and
different detection profiles:

- **Mail.Read (delegated)** — scoped to the operator identity's own mailbox in the
  sandbox. Enables self-mailbox enumeration only.
- **Mail.ReadBasic.All (application scope)** — enables cross-user enumeration across the
  tenant. (Mail.Read.All application scope similarly enables cross-user content reach.)

Operators must verify which posture is consented in cloudharbordemo before the first
Sprint 2 run; cross-user enumeration requires the application-scope grant and a one-time
admin consent (same setup pattern as the DfI prerequisite).

## Required privilege

Under the delegated Mail.Read posture, any ordinary licensed user can enumerate their own
mailbox — no role required. Cross-user enumeration requires an application-scope grant
(Mail.ReadBasic.All or Mail.Read.All) consented on the FOCI client; this is a meaningfully
higher-privilege posture and represents a post-foothold escalation, not initial-access
state.

## Procedure

*Implementation pending Sprint 2. The procedure below defines the expected implementation
shape; it will be updated to reflect the actual script behaviour when Sprint 2 opens.*

1. Operator confirms a valid Graph token from T1078.004 is in scope with the appropriate
   mail scope consented (Mail.Read delegated for self; Mail.ReadBasic.All / Mail.Read.All
   application for cross-user).
2. Operator calls GET /users/{user-id}/mailFolders and records, per folder: id,
   displayName, totalItemCount, unreadItemCount, childFolderCount.
3. Operator calls GET /users/{user-id}/messages?$top=10&$select=subject,from,
   receivedDateTime,hasAttachments to list recent messages — **metadata projection only**;
   no body content is requested in this step.
4. For a folder of interest, operator calls
   GET /users/{user-id}/mailFolders/{folder-id}/messages with the same metadata $select to
   enumerate messages within that folder.
5. Operator produces a structured summary: folder count, total/unread item counts per
   folder, recent-message metadata list, and an attachment-bearing message count.
6. A replay-log entry (kind=graph_call) is written per G-5 requirements for each distinct
   Graph call issued. Per G-7, only message metadata is recorded; message bodies are not
   read or stored.

## Guardrails

- G-1 (sandbox tenant only): all Graph calls target cloudharbordemo 76b87c33-6178-4ff9-94a7-164792c8e4c6.
- G-3 (read-only scope): GET only; no Mail.Send, no message move/delete, no mailbox-rule
  creation.
- G-5 (evidence capture): replay-log entries written per Graph call; folder/message
  metadata summary in evidence JSON.
- G-6 (audit log redaction): sender addresses, subjects, and the target UPN are hashed in
  evidence files before any content reaches the public-repo samples/ directory; raw values
  remain in the operator-side SharePoint Evidence folder only.
- G-7 (no real user data): only seeded sandbox mailboxes are targeted, and only **metadata**
  is recorded — message body content is not requested, downloaded, or stored.
- G-9 (row cap): folder and message enumeration capped at DEFAULT_ROW_CAP (default 1 000).

## Detection signals

The two permission postures generate distinct signals, and the difference is the key
detection point:

- **Delegated Mail.Read (self-mailbox):** appears as a normal user sign-in followed by the
  user reading their own mailbox via Graph. Low signal — it closely resembles legitimate
  mail-client behaviour.
- **Mail.ReadBasic.All / Mail.Read.All (application scope, cross-user):** generates a
  different sign-in and Graph-activity pattern — application-scope token acquisition and
  cross-mailbox reads from a single principal. This is **higher signal** for defenders: a
  member principal enumerating *other users'* mailboxes is a strong collection indicator
  and is the posture detection engineering should prioritise.
- MicrosoftGraphActivityLogs: GET /users/{id}/mailFolders and GET /users/{id}/messages
  from the FOCI client ID (14d82eec); cross-user variants name a target UPN distinct from
  the operator.
- Exchange Online / unified audit log: MailItemsAccessed events are logged when message
  content is read; the metadata-only enumeration here generates folder/message-listing
  events rather than content-access events.
- Microsoft Defender for Cloud Apps: cross-user mailbox enumeration is a high-fidelity
  anomaly against a normal-usage baseline.

## Limitations

- This module covers folder and message **metadata** enumeration only. Reading message
  body content (GET /users/{id}/messages/{id} with body, or downloading attachments) is
  excluded under G-3/G-7 and would require a separate guardrail review before
  implementation. The "email collection" emulation is therefore bounded to the
  inventory-and-metadata layer in Rejewski.
- T1114.002 (remote collection of mailbox content/metadata) is distinct from T1087.003
  (Account Discovery: Email Account, which enumerates *which* identities have mailboxes via
  the /users mail attributes). T1087.003 finds mailboxes; T1114.002 reaches into one.
- Cross-user enumeration depends on an application-scope grant being consented in the
  sandbox; under the delegated-only posture, the module is limited to the operator's own
  mailbox and the cross-user detection signal above will not be exercised.
- The cloudharbordemo E5 trial tenant may contain minimal seeded mailbox content. A sparse
  folder/message result is a valid emulation outcome and should be recorded as a finding.
