# T1518.001 — Software Discovery: Security Software Discovery

## Summary

Rejewski emulates an adversary who enumerates the Microsoft Defender for Identity (DfI)
sensor fleet deployed in the target tenant. An adversary with the right delegated scope can
call GET /security/identities/sensors (Microsoft Graph `microsoft.graph.security` namespace)
to retrieve every DfI sensor — one per monitored domain controller, AD FS, AD CS, or Entra
Connect host — along with each sensor's deployment status, health status, open health-issue
count, service status, version, and bound domain. From this response the adversary learns
precisely where Defender for Identity is watching and, more valuably, where it is **not**:
an un-sensored domain controller, a sensor whose service is `stopped`, or one in an
`unreachable` / `disconnected` deployment state is a detection blind spot for on-premises
Kerberos- and NTLM-based attacks. This is security-software discovery in the literal ATT&CK
sense — the adversary inventories the defensive product surface to guide later technique
selection and detection evasion.

The sensor inventory also reveals operational weakness: sensors in `outdated` or
`updateFailed` deployment status, or carrying a high `openHealthIssuesCount`, indicate a
defensive posture that is degraded and less likely to fire reliably.

Note: GET /subscribedSkus (the M365 security-product *licensing* surface) was the originally
catalogued candidate for this technique and remains a valid, complementary T1518.001 surface
— it answers "which security products are *licensed*", whereas the implemented DfI-sensor
surface answers "where is Defender for Identity actually *deployed and healthy*". The
subscribedSkus surface is deferred to a later Rejewski tool; it also carries a dual
attribution with T1526 (Cloud Service Discovery) and should be logged under both techniques
if implemented. This module governs the implemented DfI-sensor-health surface.

## Borrowed client

Microsoft Graph Command Line Tools (14d82eec-204b-4c2f-b7e8-296a70dab67e). Inherits the
borrowed-client decision from T1078.004; no separate client acquisition occurs.
No tenant-side application registration is created. The no-tenant-app-reg posture
(ADR 0001 §1, threat-model.md §3) is maintained throughout.

## Required privilege

GET /security/identities/sensors requires the `SecurityIdentitiesSensors.Read.All` delegated
scope, admin-consented on the borrowed Microsoft Graph Command Line Tools FOCI client in
cloudharbordemo. Unlike GET /users and GET /groups (Tools 1–3), DfI sensor enumeration is
gated behind a Defender XDR / Security-Reader-class grant — this is by design in Microsoft
Defender for Identity. Like CA-policy enumeration (Tool 4, T1526), it is therefore a
**post-foothold** discovery step, not a first-foothold capability: in a real engagement the
adversary must first obtain credentials for a security-role account before this enumeration
is possible. In the cloudharbordemo sandbox, meganb@cloudharbor-demo.com holds the requisite
grant to simulate that scenario.

## Procedure

1. Operator confirms a valid Graph token from T1078.004 is in scope. The token is acquired
   and silently reused through scripts/identity.py (ADR 0005 encrypted cache).
2. Operator runs `scripts/tool_dfi_health.py`, which calls
   GET /security/identities/sensors?$top=100 and follows `@odata.nextLink` until the fleet
   is exhausted (the DfI fleet returns in a single page in every realistic tenant;
   pagination is implemented defensively).
3. For each sensor the tool projects the documented evidence surface:
   `id`, `displayName`, `sensorType`, `version`, `deploymentStatus`, `healthStatus`,
   `openHealthIssuesCount`, `domainName`, `serviceStatus`, `createdDateTime`.
   - `deploymentStatus`: upToDate | outdated | updating | updateFailed | notConfigured |
     unreachable | disconnected | startFailure | syncing
   - `healthStatus`: healthy | notHealthyLow | notHealthyMedium | notHealthyHigh
   - `serviceStatus`: stopped | starting | running | disabled | onboarding | unknown
   - `sensorType`: domainControllerIntegrated | adConnectIntegrated | adfsIntegrated |
     adcsIntegrated | domainControllerStandalone
4. The tool computes an aggregate summary into the evidence JSON: total sensor count,
   healthy vs not-healthy counts, total open health issues, and per-status breakdowns
   (health, deployment, service, sensor type). These coverage-gap metrics are the
   detection-engineering payload of the run.
5. An empty fleet is handled gracefully — the tool prints "No DfI sensors found" to stderr
   and still records a graph_call replay-log entry with `row_count` (object_count) 0. It is
   never treated as an error.
6. Every emitted invocation writes a replay-log entry (kind=graph_call) per G-5, recording
   the `/security/identities/sensors` endpoint, GET method, HTTP status, and sensor count.

## Guardrails

- G-1 (consent-bound tenant lock, ADR 0008): all Graph calls target the one tenant named in the run's consent record; the evidence in this repo comes from the cloudharbordemo sandbox (76b87c33-6178-4ff9-94a7-164792c8e4c6).
- G-3 (read-only scope): GET only; no sensor configuration or deployment writes.
- G-6 (audit-log redaction): no signed PDFs, tokens, or operator filesystem paths reach any
  committed file; the token_event cache_path is redacted to "<redacted>" by
  scripts/consolidate_run.py before a run sample lands under samples/.
- G-7 (sandbox-only, no real production tenant): sensor data is read from the cloudharbordemo
  sandbox only; sensor display names and domain names are sandbox values.

## Detection signals

- MicrosoftGraphActivityLogs captures the GET /security/identities/sensors call from the
  FOCI client ID (14d82eec), including the RequestUri and the signing-in identity. This is a
  low-frequency, security-product-read operation that stands out when issued by a non-SOC
  account.
- Entra ID sign-in logs: correlatable via the T1078.004 session correlation ID.
- Microsoft Defender for Cloud Apps / XDR: a single sensor-inventory read is unlikely to
  trigger anomaly detection in isolation, but when chained with T1087.004, T1069.003, T1526,
  and T1082 reads in one session the combined read volume may surface as bulk-read anomaly
  activity.

## Evidence

## Limitations

- GET /security/identities/sensors returns DfI sensor deployment and health state only. It
  does not enumerate the broader Microsoft security-product *licensing* posture; that is the
  GET /subscribedSkus surface (deferred; see Summary note) and the GET /organization
  provisioned-plan surface (T1082).
- Sensor health/deployment enums evolve as Microsoft revises the DfI product; the tool
  surfaces the raw enum values as returned and does not normalize them, so a newly added enum
  value passes through unchanged rather than being mis-bucketed.
- The presence of a healthy sensor on a domain controller does not guarantee full detection
  coverage of that DC — sensor health reflects telemetry flow, not detection-rule efficacy.
  The tool reports posture, not assurance.
