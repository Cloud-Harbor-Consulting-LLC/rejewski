# T1526 — Cloud Service Discovery

## Summary

Rejewski emulates an adversary who, after gaining access to a privileged cloud identity
(Security Reader or higher), enumerates the Conditional Access policies configured in the
target tenant. CA policy discovery reveals the organization's security posture in detail:
which users, groups, and roles are covered by each policy; what grant controls are enforced
(MFA, compliant device, block); which cloud applications are in scope; and whether any
policies are in report-only mode (enforced in signal but not in access decisions). This
intelligence directly informs later-stage targeting — an adversary who knows which accounts
are excluded from MFA, which apps are unprotected, or which policies are disabled can exploit
those gaps in subsequent lateral movement or privilege escalation attempts.

This module sits in the Discovery tactic and represents a post-privilege-escalation step in
the Rejewski kill chain. T1526 builds on the initial access achieved via T1078.004 and the
account/group landscape established via T1087.004 and T1069.003, extending the adversary's
understanding from identity structure to access-control configuration.

## Borrowed client

Microsoft Graph Command Line Tools (14d82eec-204b-4c2f-b7e8-296a70dab67e). Inherits the
borrowed-client decision from T1078.004; no separate client acquisition occurs. The
Graph Command Line Tools client has Policy.Read.All pre-consented as a first-party Microsoft
application in most Microsoft 365 tenants, including cloudharbordemo.

No tenant-side application registration is created. The no-tenant-app-reg posture
(ADR 0001 §1, threat-model.md §3) is maintained throughout.

## Required privilege — operator prerequisite

Unlike T1087.004 (/users) and T1069.003 (/groups), which are accessible to any
ordinary licensed user, CA policy enumeration requires BOTH:

1. Policy.Read.All OAuth scope — admin-consented on the borrowed client.
2. One of the following Entra directory roles on the signed-in user:
   - Security Reader (minimum — read-only access to security resources)
   - Security Administrator
   - Conditional Access Administrator
   - Global Reader
   - Global Administrator

An ordinary licensed user without one of these roles receives HTTP 403 Forbidden.
This is by design in Microsoft Entra ID: CA policies are tenant-wide security
configuration and Microsoft enforces role-gating at the API level, not by returning
a filtered or empty result.

**Attack strategy note.** Because CA policy enumeration is gated behind a directory
role, operators conducting a realistic simulation must first model the privilege
escalation that gives the adversary that role. Common adversary paths:

- Targeted credential theft of a security administrator, help-desk operator, or
  compliance officer (accounts with the highest density of Security Reader and
  Security Administrator assignments).
- Password spray against accounts in IT operations or security groups.
- PIM role activation abuse — if the compromised account holds an eligible Security
  Reader assignment, the adversary activates the role without leaving a permanent
  role assignment artifact.
- Application-level escalation via a service principal holding Policy.Read.All at
  application permission level (Sprint 2+ Rejewski scope; not emulated in this module).

In the cloudharbordemo sandbox, meganb@cloudharbor-demo.com is assigned Security Reader
to represent a compromised security-role account. Operators running against a different
sandbox tenant must ensure the designated test account holds at least Security Reader.

## Procedure

1. Operator confirms a valid Graph token from T1078.004 is in scope and that the
   signed-in account holds Security Reader (or higher) in the target tenant.
2. Operator calls `python scripts/tool_list_ca_policies.py` which pages
   GET /identity/conditionalAccess/policies with $select and $top parameters.
3. The tool pages through all CA policies until @odata.nextLink is empty or the
   G-9 row cap is hit (default 1 000 — far above typical tenant policy counts).
4. After enumeration, the tool computes CA-specific aggregate metrics from the
   returned objects:
   - Count of enabled, disabled, and report-only policies.
   - Count of policies requiring MFA, compliant device, or block grant control.
5. Evidence JSON (policy objects + aggregate metrics) is written to stdout or --output.
6. A replay-log entry (kind=graph_call) is written per G-5 requirements.

## Guardrails

- G-1 (sandbox tenant only): all Graph calls target cloudharbordemo 76b87c33-6178-4ff9-94a7-164792c8e4c6.
- G-3 (read-only scope): GET only; no POST, PATCH, or DELETE. No CA policy modifications.
- G-5 (evidence capture): replay-log entry written per run; aggregate metrics in evidence JSON.
- G-6 (audit log redaction): policy objects are written to evidence files but contain no
  real-user PII in the sandbox (seeded test users only, per G-7). Policy display names and
  IDs are retained as-is; no redaction is applied to policy configuration fields.
- G-7 (no real user data): only seeded test accounts are referenced in policy conditions
  in the sandbox tenant.
- G-9 (row cap): enumeration capped at DEFAULT_ROW_CAP (default 1 000 policies).

## Detection signals

- Graph unified audit log: CA policy read events from the Microsoft Graph Command Line Tools
  client ID (14d82eec) on the Security Reader account, logged under the
  `conditionalAccessPolicy_get` and `conditionalAccessPolicy_list` audit categories.
- Entra ID sign-in logs: the T1078.004 sign-in session that issued the token used here
  will have correlatable correlation IDs linking the sign-in to the CA policy read.
- Microsoft Defender for Cloud Apps: anomalous policy enumeration by a non-admin account
  (Security Reader is below Global Admin) may surface as a policy-read anomaly if MDCA
  has a baseline for that account type.
- Entra ID Identity Protection: bulk API reads from a FOCI client following initial
  ROPC authentication may trigger an unusual sign-in risk signal.

## Limitations

- This module covers GET /identity/conditionalAccess/policies only. Named locations
  (GET /identity/conditionalAccess/namedLocations) are accessible with the same
  Policy.Read.All scope and are high-value for CA policy context (IP ranges, trusted
  locations) — enumeration of named locations is deferred to a follow-on tool or a
  future expansion of this module.
- Authentication strength policies (GET /identity/authenticationStrengthPolicies) are
  in beta and referenced by CA policy grantControls; full enumeration is deferred.
- This module emulates a human-account adversary (Security Reader role). An adversary
  using a service principal with application-level Policy.Read.All can enumerate CA
  policies without any directory role — that scenario is Sprint 2+ scope.
- Custom authentication factors referenced in CA policy grantControls cannot be resolved
  to full definitions via this tool (requires additional Graph endpoints).
