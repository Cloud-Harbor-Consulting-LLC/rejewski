# T1530 — Data from Cloud Storage

## Summary

Rejewski will emulate an adversary who, having discovered which cloud storage exists
(T1619), reads the content of that storage — OneDrive personal drives and Teams/group
drives reachable by the compromised identity. This is the collection action: accessing the
files themselves, not merely cataloguing where they live. GET /drives enumerates all
drives accessible to the operator identity; GET /users/{user-id}/drive/root/children lists
the root-level items in a user's OneDrive; and GET /groups/{group-id}/drive/root/children
lists the root-level items in a Teams/group drive. Where T1619 answers "what storage and
objects exist," T1530 is the step that reaches into those objects to read file metadata
and (where guardrails permit) content.

This technique is catalogued in the Collection tactic; it is the content-access phase that
follows T1619 (Cloud Storage Object Discovery) in the storage kill-chain leg. Rejewski's
read-only posture bounds T1530 to read operations; the module documents the access path,
and G-7/G-6 bound what is recorded as evidence.

## Borrowed client

Microsoft Graph Command Line Tools (14d82eec-204b-4c2f-b7e8-296a70dab67e). Inherits the
borrowed-client decision from T1078.004; no separate client acquisition occurs.
No tenant-side application registration is created. The no-tenant-app-reg posture
(ADR 0001 §1, threat-model.md §3) is maintained throughout.

Files.Read.All is required for cross-user and group drive access. Operators must verify
Files.Read.All consent status in cloudharbordemo before the first Sprint 2 run; if not
pre-consented, a one-time admin consent grant is required (same setup pattern as the DfI
prerequisite). With only the narrower delegated Files.Read, access is limited to the
operator's own OneDrive — a lower-coverage fallback surface.

## Required privilege

Files.Read.All delegated scope grants read access to files the token's scope covers,
including other users' OneDrive content and group drives — without requiring any admin
role. This broad reach from an ordinary licensed account is precisely the access posture
that makes a compromised M365 identity valuable to an adversary collecting cloud-stored
data.

## Procedure

*Implementation pending Sprint 2. The procedure below defines the expected implementation
shape; it will be updated to reflect the actual script behaviour when Sprint 2 opens.*

1. Operator confirms a valid Graph token from T1078.004 is in scope with Files.Read.All
   consented, and that a T1619 discovery pass has produced the target drive/user/group IDs.
2. Operator calls GET /drives to enumerate accessible drives; per drive: id, name,
   driveType, owner, quota.
3. For target user OneDrive: operator calls GET /users/{user-id}/drive/root/children and
   records, per item: id, name, size, file/folder facet, createdDateTime,
   lastModifiedDateTime. Folder items may be recursed within the G-9 cap.
4. For target group/Teams drive: operator calls GET /groups/{group-id}/drive/root/children
   and records the same per-item metadata.
5. Operator produces a structured inventory: drive count, per-drive item count, total size,
   and a flag for items matching a configurable sensitive-name keyword list.
6. A replay-log entry (kind=graph_call) is written per G-5 requirements for each distinct
   Graph call issued. Per G-7, only metadata is recorded in evidence; file content bytes
   are not downloaded or stored.

## Guardrails

- G-1 (sandbox tenant only): all Graph calls target cloudharbordemo 76b87c33-6178-4ff9-94a7-164792c8e4c6.
- G-3 (read-only scope): GET only; no upload, move, delete, or share operations.
- G-5 (evidence capture): replay-log entries written per Graph call; drive/item inventory
  in evidence JSON.
- G-6 (audit log redaction): file and folder names, drive names, and owner identifiers are
  hashed in evidence files before any content reaches the public-repo samples/ directory;
  raw values remain in the operator-side SharePoint Evidence folder only.
- G-7 (no real user data): only seeded sandbox content is targeted, and only **metadata**
  is recorded — file content bytes are not downloaded or written to evidence. This bounds
  the collection action to the inventory layer.
- G-9 (row cap): drive and item enumeration capped at DEFAULT_ROW_CAP (default 1 000);
  recursion depth into folders is also capped.

## Detection signals

- MicrosoftGraphActivityLogs: GET /drives, GET /users/{id}/drive/root/children, and
  GET /groups/{id}/drive/root/children from the FOCI client ID (14d82eec). Cross-user
  drive reads from a single member account are a strong collection indicator.
- OneDrive/SharePoint unified audit log: FileAccessed and FilePreviewed events are logged
  when content is read; the metadata-only enumeration in this module generates listing
  events rather than file-access events, a distinction defenders can use to separate
  inventory from content collection.
- Microsoft Defender for Cloud Apps: bulk cross-user file enumeration is a high-fidelity
  anomaly against a normal-usage baseline.
- Entra ID sign-in logs: correlatable via the T1078.004 session correlation ID.

## Limitations

- **T1530 is the collection (content-access) phase; T1619 is the preceding discovery
  phase.** The two are sequenced: T1619 establishes what storage and which objects exist,
  and T1530 reaches into those objects. This relationship is documented in both modules.
  Running T1530 without a prior T1619 pass means operating against unknown targets and is
  out of the intended workflow.
- T1530 is distinct from T1213.002 (SharePoint as an information repository). T1213.002
  covers structured SharePoint list/library *metadata* enumeration; T1530 covers file
  content access in OneDrive and group drives. The surfaces (/sites vs /drives) and the
  objective differ.
- Under G-7, this module records file/folder **metadata only**; downloading file content
  bytes (GET /drives/{id}/items/{id}/content) is not performed and would require a separate
  guardrail review. The "data from cloud storage" emulation is therefore bounded to the
  access-and-inventory layer in Rejewski.
- The cloudharbordemo E5 trial tenant may contain minimal seeded OneDrive/group content. A
  sparse result is a valid emulation outcome and should be recorded as a finding.
