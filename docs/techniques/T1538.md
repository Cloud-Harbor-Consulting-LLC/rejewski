# T1538 — Cloud Service Dashboard

## Summary

Rejewski will emulate the **programmatic** equivalent of an adversary reading a cloud
service dashboard: rather than driving the Microsoft 365 admin center GUI in a browser,
it reads the same service-health and service-usage data through the Graph
`/admin/serviceAnnouncement` and reporting endpoints. An adversary who can see which
M365 workloads are healthy, degraded, or in active incident — and which workloads have
real user activity — learns where defensive coverage may be thin and where activity will
blend in. GET /admin/serviceAnnouncement/healthOverviews returns the current health state
per workload (Exchange, SharePoint, Teams, Microsoft Defender for Identity, etc.);
GET /admin/serviceAnnouncement/issues returns active incidents and advisories; and
GET /reports/getOffice365ActiveUserDetail(period='D7') returns per-service active-user
counts. Mirroring the operational framing used in T1518.001 for DfI sensor health: a
workload reported as degraded — particularly a security workload like Defender for
Identity — signals reduced detection coverage during the degradation window.

**Scope reframing note.** T1538 was previously catalogued as out of programmatic Rejewski
scope on the basis that the technique describes human-driven GUI dashboard navigation
(Azure portal, M365 admin center, Defender/Entra portals). That exclusion is now refined:
the *interactive GUI navigation* posture remains out of scope (Rejewski drives no browser
sessions), but the *programmatic service-health and service-usage surface* exposed through
Microsoft Graph `/admin/serviceAnnouncement` and `/reports` is in scope and is catalogued
here. The two produce different telemetry — see Detection signals.

## Borrowed client

Microsoft Graph Command Line Tools (14d82eec-204b-4c2f-b7e8-296a70dab67e). Inherits the
borrowed-client decision from T1078.004; no separate client acquisition occurs.
No tenant-side application registration is created. The no-tenant-app-reg posture
(ADR 0001 §1, threat-model.md §3) is maintained throughout.

The scopes required (ServiceHealth.Read.All, Reports.Read.All) must be verified as
consented on the FOCI client in the lab tenant before the first Sprint 2 run. These are
not commonly pre-consented and may require a one-time admin consent grant in the sandbox —
the same setup pattern documented for the DfI prerequisite.

## Required privilege

ServiceHealth.Read.All and Reports.Read.All are tenant-wide read scopes; once consented
on the FOCI client, any authenticated member can call the endpoints. No directory role is
required at the API level, though tenants may apply a tenant-wide setting that obfuscates
user/site names in the reporting endpoints regardless of scope (see Limitations). This
keeps T1538 in the same low-privilege Discovery tier as the other catalogued surfaces.

## Procedure

*Implementation pending Sprint 2. The procedure below defines the expected implementation
shape; it will be updated to reflect the actual script behaviour when Sprint 2 opens.*

1. Operator confirms a valid Graph token from T1078.004 is in scope with
   ServiceHealth.Read.All and Reports.Read.All consented.
2. Operator calls GET /admin/serviceAnnouncement/healthOverviews and records, per
   workload (service): the service name and current status (e.g., serviceOperational,
   serviceDegradation, serviceInterruption, investigating, restoringService).
3. Operator calls GET /admin/serviceAnnouncement/issues and records active incidents and
   advisories: id, title, classification (incident/advisory), status, service, startDateTime,
   and isResolved. Resolved historical issues are filtered out of the active view.
4. Operator calls GET /reports/getOffice365ActiveUserDetail(period='D7') and records the
   per-service active-user counts for the trailing 7 days (Exchange, SharePoint, OneDrive,
   Teams, Yammer).
5. Operator derives a coverage-gap summary mirroring T1518.001's framing: any workload in
   a non-operational health state — especially a security workload (Defender for Identity)
   — is flagged as a reduced-detection-coverage window. Workloads with high active-user
   counts are flagged as high-blend-in activity surfaces.
6. A replay-log entry (kind=graph_call) is written per G-5 requirements for each distinct
   Graph call issued. Health/usage aggregates are written to the evidence JSON only.

## Guardrails

- G-1 (consent-bound tenant lock, ADR 0008): all Graph calls target the one tenant named in the run's consent record; the evidence in this repo comes from the lab tenant.
- G-3 (read-only scope): GET only; no service-health or reporting write operations exist
  and none are attempted.
- G-5 (evidence capture): replay-log entry written per Graph call; health/usage aggregates
  in evidence JSON.
- G-6 (audit log redaction): any user- or site-identifying values returned by the reporting
  endpoint are hashed in evidence files before any content reaches the public-repo samples/
  directory; raw values remain in the operator-side SharePoint Evidence folder only.
- G-7 (no real user data): only seeded sandbox tenant data is read; the reporting endpoint
  returns aggregate counts, not user content.
- G-9 (row cap): issue and per-service enumeration capped at DEFAULT_ROW_CAP (default 1 000).

## Detection signals

- MicrosoftGraphActivityLogs: GET /admin/serviceAnnouncement/healthOverviews,
  /admin/serviceAnnouncement/issues, and /reports/getOffice365ActiveUserDetail from the
  FOCI client ID (14d82eec). This is the **distinguishing signal**: the programmatic
  Rejewski emulation produces Graph-API audit events, whereas the GUI-driven T1538 posture
  (out of scope here) would instead produce interactive admin-center session and portal
  sign-in signals. Defenders relying solely on portal-session telemetry to detect T1538
  will miss the programmatic service-health read.
- Microsoft Defender for Cloud Apps: service-health and reporting reads by a non-admin
  member account are anomalous against a normal-usage baseline.
- Entra ID sign-in logs: correlatable via the T1078.004 session correlation ID.

## Limitations

- The *interactive GUI dashboard* posture of T1538 — a human driving the Azure portal,
  M365 admin center, Defender portal, or Entra admin center with stolen credentials —
  remains out of Rejewski scope. Rejewski drives no browser sessions; this module covers
  only the programmatic Graph service-announcement and reporting surface. Detection
  coverage for GUI-driven T1538 must come from portal-session telemetry sourced elsewhere.
- The tenant-wide "Reports" concealment setting (M365 admin center → Org settings →
  Reports) replaces user, group, and site names with anonymised identifiers in the
  reporting endpoints regardless of the caller's scope. If enabled in the lab tenant, the
  active-user detail will be de-identified; this is a valid emulation outcome and is
  recorded as a finding.
- serviceAnnouncement health/issues reflect Microsoft-published service state, not
  tenant-specific outages of customer workloads. The technique reveals platform-side
  coverage windows, not on-premises or customer-app availability.
- This technique reads service health and usage; it does not read message content,
  mailbox data, or file content (those map to T1114.002, T1530, and T1213.002/.003).
