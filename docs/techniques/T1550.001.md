# T1550.001 — Use Alternate Authentication Material: Application Access Token

## Summary

Rejewski emulates an adversary who, having captured a delegated refresh token for a
borrowed first-party OAuth client, reuses that token to acquire fresh Microsoft Graph
access tokens silently across many tool invocations — without re-running the interactive
credential grant each time. Rather than presenting the user's password on every call, the
adversary holds one session and redeems it repeatedly, exactly as Midnight Blizzard and
Octo Tempest hold a single credentialed session across an entire intrusion. This is the
defense-evasion / lateral-movement layer of the Rejewski kill chain: T1078.004 acquires the
session on first sign-in, and T1550.001 operationalises the resulting token so that every
downstream discovery technique (T1087.004, T1069.003, T1526) runs off reused authentication
material instead of fresh password grants. The implementation basis is
[scripts/identity.py](../../scripts/identity.py), the shared MSAL token-acquisition helper
shipped in Sprint 1 W2 (Tue 2026-05-19) per ADR 0005.

## Borrowed client

Microsoft Graph Command Line Tools (`14d82eec-204b-4c2f-b7e8-296a70dab67e`). This is the
default borrowed first-party client decided in ADR 0004 §4 and refined in ADR 0005 §4: a
Microsoft-published client that the target tenant already trusts, carrying tenant-level
pre-consent for delegated Graph scopes. Borrowing it means no Rejewski-controlled
application object is ever registered in the sandbox tenant — the no-tenant-app-reg posture
(ADR 0001 §1, G-2) holds throughout. Because the borrowed client and the persisted
refresh token are both Microsoft-native artifacts, the on-disk cache and the reissued
tokens are structurally identical to what `Connect-MgGraph` would produce for the same
client ID; the reuse does not advertise itself as adversary tooling.

Note on FOCI: the default client (`14d82eec`) is **not** a confirmed FOCI member. Sprint 2+
techniques that depend on verified cross-client refresh-token reuse must switch to the
Azure CLI client (`04b07795-8ddb-461a-bbee-02f9e1bf7b46`) per ADR 0004 §4 / ADR 0005 §4.
This module exercises same-client refresh-token reuse only, for which `14d82eec` is correct.

## Token persistence and silent reuse

The reuse mechanism is the heart of this technique and is implemented end-to-end in
[scripts/identity.py](../../scripts/identity.py) `acquire_token(...)`:

1. **Encrypted persistence.** The borrowed refresh token is stored through
   msal-extensions' `PersistedTokenCache` wrapping `build_encrypted_persistence(path)`,
   which binds an OS-native encryption backend automatically (DPAPI on Windows, Keychain on
   macOS, libsecret on Linux). Cache path defaults to a per-actor slug under the platform
   cache directory (`%LOCALAPPDATA%\rejewski\<slug>.bin`,
   `~/Library/Caches/rejewski/<slug>.bin`, `~/.cache/rejewski/<slug>.bin`) and is
   overridable via `REJEWSKI_CACHE_PATH`.
2. **Plaintext refusal.** When no OS-native encryption backend is available (typical on
   headless Linux without an unlocked Secret Service), the helper refuses to fall back to
   plaintext `FilePersistence` unless `REJEWSKI_ALLOW_PLAINTEXT_CACHE=1` is set. The opt-in
   is recorded as `persistence_kind: "plaintext"` in every token_event entry it produces.
3. **Silent redemption.** On a cache hit the helper calls
   `acquire_token_silent_with_error` (the lossy `acquire_token_silent` is forbidden) to
   reissue an access token from the cached refresh token — no password is materialised. On a
   cache miss it falls back to the T1078.004 ROPC grant once, seeding the cache for all
   subsequent silent reuse.
4. **CAE awareness.** The `PublicClientApplication` is built with
   `client_capabilities=["CP1"]` so Continuous Access Evaluation claims challenges surface
   structurally rather than as opaque 401s, matching Midnight Blizzard-tier session
   handling (ADR 0005 §2–§3).

## Procedure

1. Operator runs the first technique tool. The actor's cache is empty, so
   `scripts/identity.acquire_token(...)` falls back to the ROPC grant (T1078.004) against
   the seeded compromised-user password and writes the borrowed refresh token to the
   encrypted cache. Flow is recorded as `ropc`.
2. Every subsequent tool routes its token acquisition through the same
   `scripts/identity.acquire_token(...)` entry point. The helper finds the cached account,
   calls `acquire_token_silent_with_error`, and returns a fresh access token with no
   password grant. Flow is recorded as `silent`.
3. Each acquisition — silent or ROPC — emits a `token_event` replay-log entry recording the
   token endpoint, flow, requested scopes, outcome, AADSTS code (on error), correlation id,
   persistence kind, and cache path. Access, refresh, and id tokens are never written.
4. The reissued access token is handed to the calling discovery tool (T1087.004,
   T1069.003, T1526), which performs its Graph reads under reused authentication material.
5. Concurrent tool runs serialise their cache writes through msal-extensions' bundled
   portalocker, so refresh-token rotation does not hand a stale token to a parallel tool.

All inline MSAL usage in technique tools is forbidden (ADR 0005 §7); `scripts/identity.py`
is the single entry point, which is what guarantees a `token_event` is emitted for every
acquisition.

## Guardrails

- **G-1 (consent-bound tenant lock, ADR 0008):** every token request and downstream Graph call
  targets the one tenant named in the run's consent record; `identity.acquire_token` checks it
  before any token request and `replay_log.write_entry` refuses evidence for any other tenant.
- **G-2 (no tenant app registration):** only the borrowed first-party client is used; no
  Rejewski application object is created to hold or redeem the token.
- **G-3 (consent floor):** reused tokens carry only the read-only Sprint 1 Graph scopes;
  refresh-token reuse never widens scope beyond what the original grant obtained. The helper
  does not narrow or escalate scope.
- **G-4 (FOCI client allowlist):** acquisition uses the approved client `14d82eec` (default);
  the Azure CLI fallback is the only other permitted client and is not used in this module.
- **G-6 (audit log redaction):** the `cache_path` recorded in every token_event is redacted
  before publication (see [consolidate_run.py](../../scripts/consolidate_run.py)), and the
  sandbox tenant GUID is the only tenant identifier retained. Tokens are never logged.
- **G-7 (no real user data):** the actor whose refresh token is reused is a seeded sandbox
  test account (e.g. meganb@<lab-domain>); no real CHC or customer identity is ever
  cached or replayed.
- **G-8 (time-boxed sessions):** Sprint 1 reuse stays within the session-keep-warm window;
  refresh tokens are not held beyond it. Long-lived token survival is a Sprint 2+ persistence
  technique, not part of this module.

## Detection signals

- **MicrosoftGraphActivityLogs:** every reissued access token drives Graph reads that appear
  in `MicrosoftGraphActivityLogs` (when enabled) carrying the borrowed client ID
  (`14d82eec`), a delegated token, and the endpoint path. The differentiator from legitimate
  Graph CLI admin use is volumetric and behavioural — long-running sessions, scope diversity
  over time, and IP/UA drift — not the app ID, which cannot be blocked without breaking real
  admin tooling.
- **Entra ID sign-in logs:** each silent redemption produces a non-interactive sign-in entry
  with `appId=14d82eec…`, `clientAppUsed=Mobile Apps and Desktop clients`, and
  `tokenIssuerType=AzureAD`. The absence of a fresh interactive sign-in between many Graph
  read bursts is itself the reuse tell.
- **Entra ID Identity Protection:** the initial ROPC seeding may fire `unfamiliarFeatures`
  on a new ASN/IP/UA; subsequent silent reuse bypasses MFA by design (the refresh token has
  already redeemed claims), so detection shifts from sign-in risk to session-anomaly signals.
- **Rejewski replay log (`token_event` kind):** every acquisition is self-instrumented as a
  `kind: "token_event"` replay-log entry emitted by `scripts/identity.py`, with the nested
  `technique.id = "T1550.001"`. These entries (see the R007 sample below) are the
  ground-truth audit surface used downstream to validate that reuse detection coverage
  matches what the tool actually did.

## Limitations

- This module covers **same-client** refresh-token reuse only (`14d82eec` → `14d82eec`).
  Cross-client / FOCI refresh-token theft (redeeming one client's refresh token for another
  client's access token) requires the confirmed-FOCI Azure CLI client and is deferred to
  Sprint 2+.
- Token survival beyond the G-8 session-keep-warm window (durable persistence) is out of
  scope; Sprint 1 reuse is bounded to the active session.
- Pass-the-cookie / web-session material (browser auth cookies, PRT) is a sibling alternate
  authentication-material surface and is not exercised here.
- The reuse path bypasses MFA only because the original grant already redeemed claims; this
  module does not emulate forging or stealing the *initial* token (T1606) — it reuses a token
  obtained legitimately-for-the-simulation via T1078.004.
