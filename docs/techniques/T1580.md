# T1580 — Cloud Infrastructure Discovery

## Summary

Rejewski emulates an adversary who, holding a valid cloud identity, enumerates the
tenant's Microsoft Purview sensitivity-label inventory via Microsoft Graph
GET /security/dataSecurityAndGovernance/sensitivityLabels. The sensitivity-label
collection answers a tightly-scoped infrastructure-discovery question: how is this
tenant choosing to *classify* its data, which labels are actively enforced
(`isEnabled`), and where (email, file, teamwork) is each label allowed to apply
(`applicableTo`). From this one read an adversary derives the defender's
data-protection posture without ever touching the content the labels guard:
which labels carry endpoint protection (`isEndpointProtectionEnabled`), which
apply automatically vs by recommendation vs only when the user picks them
(`actionSource`), the priority ordering, and the sub-label tree (Confidential /
Highly Confidential variants). That posture map directly informs later-stage
Collection targeting — labels that are defined but `isEnabled: false`, or labels
with no endpoint protection guard, identify data classes that are nominally
classified but operationally unguarded.

Note: GET /organization (tenant top-level configuration: hybrid status, verified
domains, provisioned plans, notification contacts), GET /domains (registered
domain list and federation posture), and GET /subscribedSkus (licensed SKUs and
service-plan inventory) were the originally-catalogued candidate surfaces for
this technique and remain valid, complementary T1580 surfaces — they answer
"what is the tenant" and "which Microsoft security products are licensed", whereas
the implemented sensitivity-label surface answers "how is the tenant choosing to
classify and protect its data". The org/domains/subscribedSkus surfaces are
deferred complementary surfaces (not discarded — see Limitations) and overlap
with surfaces already governed by T1082 and T1518.001 modules. This module
governs the implemented Purview sensitivity-label surface.

## Required privilege

GET /security/dataSecurityAndGovernance/sensitivityLabels requires the
`SensitivityLabel.Read` delegated scope, admin-consented on the borrowed
Microsoft Graph Command Line Tools FOCI client in cloudharbordemo. Unlike
CA-policy (T1526), DfI-sensor (T1518.001), and managed-device (T1082)
enumeration, **no Entra directory role is required** on the signed-in user — any
authenticated member with the scope consented can read the tenant's label
inventory. This keeps T1580 at the same low privilege tier as the other
Discovery-leg techniques, runnable immediately after the T1078.004 initial-access
step. In the cloudharbordemo sandbox, meganb@cloudharbor-demo.com is a delegated
member account with the `SensitivityLabel.Read` scope consented via the borrowed
client.

## Procedure

1. Operator confirms a valid Graph token from T1078.004 is in scope. The token is
   acquired and silently reused through scripts/identity.py (ADR 0005 encrypted
   cache).
2. Operator runs `scripts/tool_purview_labels.py`, which calls
   GET /security/dataSecurityAndGovernance/sensitivityLabels with `$top=100`,
   then follows `@odata.nextLink` until exhausted or the G-9 row cap is hit. The
   label collection returns in a single page in every realistic tenant;
   pagination is implemented defensively.
3. The tool projects each label down to the documented evidence surface:
   `id`, `name`, `description`, `priority`, `isEnabled`,
   `isEndpointProtectionEnabled`, `actionSource`, `applicableTo`, `sublabels`.
4. The tool computes an aggregate summary into the evidence JSON: total label
   count, enabled vs disabled counts, applicableTo coverage breakdown (how many
   labels apply to email vs file vs teamwork), labels with sub-labels, and
   actionSource distribution (manual / automatic / recommended). These are the
   detection-engineering and targeting payload of the run.
5. An empty inventory (tenant with no Purview labels configured) is handled
   gracefully — the tool prints "No sensitivity labels found" to stderr and still
   records a graph_call replay-log entry with `row_count` (object_count) 0. It is
   never treated as an error.
6. Every emitted invocation writes a replay-log entry (kind=graph_call) per G-5,
   recording the `/security/dataSecurityAndGovernance/sensitivityLabels`
   endpoint, GET method, HTTP status, page count, and the total label count
   across all pages.

## Guardrails

- G-1 (sandbox tenant only): all Graph calls target cloudharbordemo 76b87c33-6178-4ff9-94a7-164792c8e4c6.
- G-3 (read-only scope): GET only; no label create, update, publish, or delete.
- G-5 (evidence capture): replay-log entry written per Graph call; aggregate label
  summary in evidence JSON.
- G-6 (audit log redaction): label `name` and `description` are written to the
  evidence file in cleartext (sandbox tenant values only); operator reviews before
  any public-repo sample commit.
- G-7 (no real user data): only the seeded sandbox tenant's own configuration is
  read; no per-user data is touched.
- G-9 (row cap): sensitivity-label enumeration capped at DEFAULT_ROW_CAP (default
  1 000).

## Detection signals

- MicrosoftGraphActivityLogs captures the
  GET /security/dataSecurityAndGovernance/sensitivityLabels call from the FOCI
  client ID (14d82eec), including the RequestUri and the signing-in identity. A
  full sensitivity-label read from a member account is a strong recon indicator
  — labels are tenant-wide data-protection configuration, not per-user content,
  and ordinary users rarely enumerate the inventory.
- Entra ID sign-in logs: correlatable via the T1078.004 session correlation ID.
- Microsoft Defender for Cloud Apps: bulk sensitivity-label reads by a non-admin
  account may surface as anomalous activity against a baseline of normal API
  usage.
- Note the reflexive signal: an adversary reading the label inventory is
  specifically trying to learn which data classes *would* trigger protection if
  later collected. Defenders should treat sensitivity-label reads from a member
  account as a high-context recon indicator, especially when chained with
  Collection-leg techniques in the same session.

## Limitations

- **Deferred complementary surfaces.** The originally-catalogued T1580 surfaces
  remain valid complementary reads and are deferred to follow-on tools rather
  than discarded:
  - GET /organization is the primary surface of T1082 (System Information
    Discovery) and a deferred T1526 surface. T1580 would read it for the broader
    *infrastructure profile* (org + domains + licenses together); the current
    implementation defers that read to the existing T1082 tool
    (scripts/tool_intune_devices.py governs the implemented T1082 surface).
  - GET /subscribedSkus is a catalogued T1518.001 (Security Software Discovery)
    surface. T1580 would use it for the licensed-SKU *inventory*; T1518.001
    reads it to assess active security-software posture specifically. When both
    are implemented, the license read should be issued once and shared, not
    duplicated per technique.
  - GET /domains is also exercised by T1482 (Domain Trust Discovery). T1580
    would record domain *existence and count*; T1482 analyses federation/trust
    relationships per domain.
- A tenant with no Purview labels configured (smaller tenants without
  Microsoft Purview Information Protection enabled) returns an empty array. The
  tool treats this as a successful empty-inventory outcome, not an error — that
  is itself an infrastructure-discovery finding (the tenant has no
  data-classification layer to interfere with later Collection-leg techniques).
- The sensitivity-label inventory describes the *defined* classification scheme,
  not which content currently *carries* a label. Per-object label assignment is
  out of scope here and would require enumerating files/messages via Sites,
  Drives, or Mail surfaces (catalogued separately under T1213.002, T1530,
  T1213.003, T1114.002).
- No Azure resource-manager (ARM) infrastructure (subscriptions, resource
  groups, VMs) is in scope — Rejewski reads Microsoft Graph only. ARM-level
  cloud infrastructure discovery requires the Azure Resource Manager API,
  outside current scope.
