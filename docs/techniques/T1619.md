# T1619 — Cloud Storage Object Discovery

## Summary

Rejewski will emulate an adversary who, holding a valid cloud identity, enumerates the
cloud storage available to that identity and the objects within it — before reading any
file content. This is the discovery phase that precedes T1530 (Data from Cloud Storage):
it answers "what storage exists and what objects are present," establishing the target set
that T1530 later reaches into. GET /drives lists all drives visible to the operator;
GET /drives/{drive-id}/root/children enumerates the objects at a drive's root; and
GET /sites/{site-id}/drives enumerates the drives attached to SharePoint sites. The output
is an inventory of drives and root-level objects — names, sizes, types, and timestamps —
that maps the storage attack surface without committing to the higher-signal content reads.

This technique is catalogued in the Discovery tactic. It is the first step in the storage
kill-chain leg; T1530 is the collection step that follows. Rejewski's read-only posture
means T1619 records drive and object metadata only.

## Borrowed client

Microsoft Graph Command Line Tools (14d82eec-204b-4c2f-b7e8-296a70dab67e). Inherits the
borrowed-client decision from T1078.004; no separate client acquisition occurs.
No tenant-side application registration is created. The no-tenant-app-reg posture
(ADR 0001 §1, threat-model.md §3) is maintained throughout.

Files.Read.All and Sites.Read.All are required for full drive and site-drive enumeration.
Operators must verify consent status in cloudharbordemo before the first Sprint 2 run; if
not pre-consented, a one-time admin consent grant is required (same setup pattern as the
DfI prerequisite). With only the narrower delegated Files.Read, discovery is limited to the
operator's own drive — a lower-coverage fallback surface.

## Required privilege

Files.Read.All (and Sites.Read.All for site-attached drives) delegated scopes grant
read access to the drives and objects the token's scope covers, without any admin role.
The breadth of this read access from an ordinary account is the posture that makes a
compromised M365 identity valuable for mapping cloud storage in real engagements.

## Procedure

*Implementation pending Sprint 2. The procedure below defines the expected implementation
shape; it will be updated to reflect the actual script behaviour when Sprint 2 opens.*

1. Operator confirms a valid Graph token from T1078.004 is in scope with Files.Read.All
   and Sites.Read.All consented.
2. Operator calls GET /drives to list all drives visible to the operator identity; per
   drive: id, name, driveType, owner, quota (total, used, remaining).
3. For each drive of interest, operator calls GET /drives/{drive-id}/root/children and
   records, per object: id, name, size, file/folder facet, createdDateTime,
   lastModifiedDateTime.
4. For SharePoint sites surfaced via T1213.002/T1619, operator calls
   GET /sites/{site-id}/drives to enumerate site-attached document-library drives and
   records the same per-drive metadata.
5. Operator produces a structured inventory: drive count by type, object count per drive,
   total storage consumed, and a flag for objects matching a configurable sensitive-name
   keyword list — handed off as the target set for a T1530 collection pass.
6. A replay-log entry (kind=graph_call) is written per G-5 requirements for each distinct
   Graph call issued.

## Guardrails

- G-1 (sandbox tenant only): all Graph calls target cloudharbordemo 76b87c33-6178-4ff9-94a7-164792c8e4c6.
- G-3 (read-only scope): GET only; no object content reads, no upload/move/delete. This
  module covers drive and object **metadata** enumeration only.
- G-5 (evidence capture): replay-log entries written per Graph call; drive/object inventory
  in evidence JSON.
- G-6 (audit log redaction): drive names, object names, and owner identifiers are hashed in
  evidence files before any content reaches the public-repo samples/ directory; raw values
  remain in the operator-side SharePoint Evidence folder only.
- G-7 (no real user data): object content is not read; only seeded sandbox storage is
  enumerated, and only metadata is recorded.
- G-9 (row cap): drive and object enumeration capped at DEFAULT_ROW_CAP (default 1 000);
  recursion depth into folders is also capped.

## Detection signals

- MicrosoftGraphActivityLogs: GET /drives, GET /drives/{id}/root/children, and
  GET /sites/{id}/drives from the FOCI client ID (14d82eec). Broad drive enumeration from a
  single member account is a storage-reconnaissance indicator.
- OneDrive/SharePoint unified audit log: listing/enumeration events are logged distinctly
  from file-access events. T1619 generates listing events (object discovery); the follow-on
  T1530 generates FileAccessed events (content collection). Defenders correlating the two
  can see the discovery-then-collection progression.
- Microsoft Defender for Cloud Apps: bulk drive enumeration is an anomaly against a normal-
  usage baseline.
- Entra ID sign-in logs: correlatable via the T1078.004 session correlation ID.

## Limitations

- **T1619 is the discovery phase (what storage exists, what objects are present); T1530 is
  the collection phase (accessing the content).** The sequencing is intentional and is
  documented in both modules: a T1619 pass produces the drive/user/group/object target set
  that a subsequent T1530 pass reaches into. T1619 stops at the inventory; it does not read
  object content.
- This module records drive and object **metadata only**; reading object content
  (GET /drives/{id}/items/{id}/content) is the T1530 collection action and is out of scope
  for T1619.
- T1619 shares Graph surface with T1530 (GET /drives) and with T1213.002/.003
  (GET /sites/{id}/drives). The distinction is intent and depth: T1619 inventories storage
  objects; T1213.002 inventories SharePoint list/library metadata; T1530 accesses file
  content.
- The cloudharbordemo E5 trial tenant may contain minimal seeded storage. A sparse drive/
  object result is a valid emulation outcome and should be recorded as a finding.
