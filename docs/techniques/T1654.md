# T1654 — Log Enumeration

This module covers two Graph surfaces, both mapped to T1654 because both enumerate
security log data that reveals what the defender can see. **Surface A** reads the
tenant's authentication telemetry via `GET /auditLogs/signIns` (Tool 10). **Surface B**
reads the defender's own Defender XDR alert queue via `GET /security/alerts_v2`
(Tool 12) — what has already been detected, and what has not.

## Surface A — Sign-In Logs

### Summary

Rejewski emulates an adversary who, holding a valid cloud identity with the
Reports Reader (or higher) role, reads Entra ID sign-in logs via Microsoft
Graph GET /auditLogs/signIns to map the tenant's authentication patterns: who
has signed in, from where, with which apps, with what risk level, and with what
success/failure outcome. Sign-in log access reveals admin account activity
(when and from where the highest-privilege accounts authenticate), service
principal authentication events (active automation and integrations), and
non-interactive sign-ins (token-reuse and long-lived session indicators). An
adversary uses this telemetry to identify high-value targets, understand the
defender's own monitoring baseline, and detect long-dwell sessions that may
have gone unnoticed.

The log read is itself the discovery — no content collection happens here; only
the metadata that tells the adversary where to look next and how the defender's
own monitoring baseline behaves. Because the read is reflexive (an adversary
reading the very telemetry that records the read), this technique is a strong
detection-engineering test surface: a member-account user reading sign-in logs
should itself appear as a Defender for Cloud Apps anomaly.

### ATT&CK reference

<https://attack.mitre.org/techniques/T1654/>

### Borrowed client

Microsoft Graph Command Line Tools (14d82eec-204b-4c2f-b7e8-296a70dab67e). Inherits the
borrowed-client decision from T1078.004; no separate client acquisition occurs.
No tenant-side application registration is created. The no-tenant-app-reg posture
(ADR 0001 §1, threat-model.md §3) is maintained throughout.

### Required privilege — operator prerequisite

Unlike T1087.004 (/users) and T1069.003 (/groups), which are accessible to any
ordinary licensed user, sign-in log enumeration requires BOTH:

1. `AuditLog.Read.All` OAuth scope — admin-consented on the borrowed Microsoft
   Graph Command Line Tools client in the lab tenant.
2. One of the following Entra directory roles on the signed-in user:
   - Reports Reader (minimum — read-only access to reports and sign-in logs)
   - Security Reader
   - Security Operator
   - Security Administrator
   - Global Reader
   - Global Administrator

An authenticated member without one of these roles receives HTTP 403 Forbidden
regardless of scope consent. This is by design in Microsoft Entra ID: sign-in
logs are tenant-wide security telemetry and Microsoft enforces role-gating at
the API level, not by returning a filtered or empty result. This is the same
role-gated pattern as CA-policy enumeration (T1526 requires Security Reader).

**Attack strategy note.** Because sign-in log enumeration is gated behind a
directory role, this is a **post-foothold, post-privilege** step in the kill
chain — the adversary first establishes the T1078.004 initial access on an
ordinary member account, then escalates to a Reports Reader / Security Reader
role before running this tool. Common adversary paths to that role:

- Targeted credential theft of a reports/help-desk operator, security analyst,
  or compliance officer (accounts with the highest density of Reports Reader and
  Security Reader assignments).
- Password spray against accounts in IT operations or security groups.
- PIM role activation abuse — if the compromised account holds an eligible
  Reports Reader or Security Reader assignment, the adversary activates the
  role without leaving a permanent role-assignment artifact.
- Application-level escalation via a service principal holding
  `AuditLog.Read.All` at application permission level (Sprint 2+ Rejewski
  scope; not emulated in this module).

In the lab tenant, meganb@<lab-domain> must be assigned
Reports Reader (or higher) before this tool will return a non-403 response.
Operators running against a different sandbox tenant must ensure the designated
test account holds at least Reports Reader.

### Procedure

1. Operator confirms a valid Graph token from T1078.004 is in scope and that the
   signed-in account holds Reports Reader (or higher) in the target tenant. The
   token is acquired and silently reused through scripts/identity.py (ADR 0005
   encrypted cache).
2. Operator runs `scripts/tool_signin_logs.py`, which composes a MANDATORY
   `$filter=createdDateTime ge <window-start>` clause (default window: last 7
   days, configurable via `--days`). Without the date filter,
   /auditLogs/signIns times out on large tenants.
3. The tool issues GET /auditLogs/signIns with `$top=100` and the configured
   `$select` projection (`id, createdDateTime, userDisplayName,
   userPrincipalName, userId, appId, appDisplayName, ipAddress, clientAppUsed,
   isInteractive, riskLevelAggregated, riskState, status`), then follows
   `@odata.nextLink` until exhausted or the G-9 row cap is hit (default 1 000;
   cap applies to total sign-ins collected, not per page).
4. After enumeration, the tool computes aggregate metrics into the evidence
   JSON: `total_sign_ins`, `interactive_count`, `non_interactive_count`,
   `by_risk_level`, `failed_count`, `unique_apps`, `unique_users`. These are
   the detection-engineering and targeting payload of the run.
5. An empty window (no sign-ins matching the filter) is handled gracefully —
   the tool prints "No sign-ins found for the specified period" to stderr and
   still records a graph_call replay-log entry with `row_count` (object_count)
   0. It is never treated as an error.
6. Every emitted invocation writes a replay-log entry (kind=graph_call) per
   G-5, recording the `/auditLogs/signIns` endpoint, GET method, HTTP status,
   page count, and the total sign-in count across all pages.

### Guardrails

- G-1 (consent-bound tenant lock, ADR 0008): all Graph calls target the one tenant named in the run's consent record; the evidence in this repo comes from the lab tenant.
- G-3 (read-only scope): GET only; no write to audit/sign-in logs.
- G-5 (evidence capture): replay-log entry written per Graph call; aggregate
  metrics in evidence JSON.
- G-6 (audit log redaction): sandbox user UPNs/IPs are retained in the evidence
  JSON for analysis; reviewed before any public-repo sample commit.
- G-7 (no real user data): only the seeded sandbox tenant's own sign-in events
  are read; all UPNs and userIds are sandbox values.
- G-9 (row cap): sign-in enumeration capped at DEFAULT_ROW_CAP (default 1 000)
  applied to total sign-ins collected, not per page.

### Detection signals

- MicrosoftGraphActivityLogs captures the GET /auditLogs/signIns call from the
  FOCI client ID (14d82eec) as a GET to `/auditLogs/signIns`, including the
  RequestUri (with the `$filter` and `$select` projections) and the signing-in
  identity.
- Entra ID audit logs record `AuditLog.Read` operations against the
  /auditLogs/signIns endpoint.
- **Reflexive signal — a member-account user reading sign-in logs is itself
  anomalous** and should trigger a Defender for Cloud Apps alert. An adversary
  reading this very telemetry to plan further action is exactly the threat
  /auditLogs/signIns access controls exist to surface; defenders should baseline
  per-account access to this endpoint and alert on the first non-baseline read.
- Entra ID sign-in logs: correlatable via the T1078.004 session correlation ID.

### Evidence

- samples/replay-log/R009.json — consented run R009 (the lab tenant,
  2026-06-23): graph_call entry for tool_signin_logs,
  GET /auditLogs/signIns with $filter=createdDateTime ge 2026-06-16T12:54:41Z
  and the v1.0 $select projection, 53 sign-ins enumerated in 1 page,
  outcome=success. meganb@<lab-domain> holds the Reports Reader (or
  higher) role required by the endpoint; the run also returned aggregate
  metrics into the evidence JSON (53 interactive, 0 non-interactive,
  failed_count 8, unique_apps 11, unique_users 2). Same run also carries the
  T1580 graph_call entry (outcome=success, 4 sensitivity labels enumerated) and
  the two T1550.001 token_event entries.

### Limitations

- Sign-in logs are retained for 30 days (Entra ID P1/P2) or 7 days (free Entra
  tier). The `--days` lookback is capped at the tenant's retention window;
  historical dwell analysis beyond 30 days requires Microsoft Sentinel or Log
  Analytics export and is out of scope for this tool.
- The `appliedConditionalAccessPolicies` field on each sign-in event requires
  additional CA-read permissions and is not part of the `$select` projection
  here; CA-policy correlation is the role of T1526
  (scripts/tool_list_ca_policies.py).
- The `signInEventType` property (which classifies a sign-in as
  `interactiveUser`, `nonInteractiveUser`, `servicePrincipal`, or
  `managedIdentity`) is exposed **only on the Microsoft Graph beta endpoint**;
  on `/v1.0/auditLogs/signIns` it returns HTTP 400 ("Could not find a property
  named 'signInEventType' on type 'microsoft.graph.signIn'"). v1.0 returns
  interactive user sign-ins; this module uses `isInteractive` for the
  evidence-level interactive/non-interactive split and defers richer event-type
  classification to a future beta-endpoint module.
- Non-interactive sign-ins (token reuse, refresh-token flows) may be absent on
  free Entra licenses — the non-interactive sign-in log requires Entra ID P1
  or higher.
- This module emulates a human-account adversary (Reports Reader role). An
  adversary using a service principal with application-level
  `AuditLog.Read.All` can enumerate sign-in logs without any directory role —
  that scenario is Sprint 2+ scope and not emulated in this module.
- The /auditLogs/signIns endpoint does not return Microsoft Graph activity logs
  themselves (MicrosoftGraphActivityLogs is a separate Azure Monitor / Log
  Analytics surface, not a Graph endpoint); Graph-call telemetry collection is
  out of scope for this tool.

## Surface B — Security Alerts

### Summary

Rejewski emulates an adversary who, holding a valid cloud identity with the Security Reader
(or higher) role, reads Defender XDR security alerts via Microsoft Graph GET /security/alerts_v2
to determine what the defender has already detected. Security alerts expose the defender's
detection coverage: which alert categories are firing, which alerts are active versus resolved,
and whether any in-progress investigations are assigned. An adversary with this view can
identify whether their earlier enumeration activity (T1087.004, T1526, T1580) has generated
alerts, select techniques and timing to avoid future detection, and confirm whether
post-compromise activity has been noticed.

Reading security alerts is reflexive: an adversary reading the defender's own alert queue
from inside the tenant should itself generate a Defender for Cloud Apps anomaly on the first
non-baseline read from a member account.

### Required privilege — operator prerequisite

Security alert enumeration requires BOTH:

1. `SecurityAlert.Read.All` OAuth scope — admin-consented on the borrowed Microsoft Graph
   Command Line Tools client (14d82eec-204b-4c2f-b7e8-296a70dab67e) in the lab tenant.
2. One of the following Entra directory roles on the signed-in user:
   - Security Reader (minimum)
   - Security Operator
   - Security Administrator
   - Global Reader
   - Global Administrator

A member account without one of these roles receives HTTP 403 regardless of scope consent.

In the lab tenant, meganb@<lab-domain> must hold Security Reader
(or higher) before this tool will return a non-403 response.

### Procedure

1. Operator confirms a valid Graph token from T1078.004 is in scope and that the signed-in
   account holds Security Reader (or higher) in the target tenant. Token is acquired and
   silently reused through scripts/identity.py (ADR 0005).
2. Operator runs `scripts/tool_list_security_alerts.py`. Default window: last 30 days
   (`--days 30`). Optional filters: `--severity`, `--status`.
3. The tool issues GET /security/alerts_v2 with `$top=100` and the configured `$select`
   projection (`id, title, severity, status, classification, determination, category,
   alertType, createdDateTime, lastModifiedDateTime, assignedTo`), then follows
   `@odata.nextLink` until exhausted or the G-9 row cap is hit.
4. After enumeration, the tool computes aggregate metrics: `total_alerts`, `by_severity`,
   `by_status`, `by_category`. These metrics reveal how the defender's alert coverage is
   distributed across severity and category.
5. An empty result (no alerts matching the filter) is handled gracefully — the tool prints
   "No alerts found for the specified period" to stderr and still records a `graph_call`
   replay-log entry with `object_count` 0.
6. Every invocation writes a `graph_call` replay-log entry per G-5, recording the
   `/security/alerts_v2` endpoint, GET method, HTTP status, page count, and total alert count.

### Guardrails

- G-1 (consent-bound tenant lock, ADR 0008): all Graph calls target the one tenant named in the run's consent record; the evidence in this repo comes from the lab tenant.
- G-3 (read-only scope): GET only; no write to security alerts.
- G-5 (evidence capture): replay-log entry written per Graph call; aggregate metrics in
  evidence JSON.
- G-6 (data redaction): alert titles and assignedTo values are sandbox values; review before
  any public-repo sample commit.
- G-7 (no real user data): only the seeded sandbox tenant's own alerts are read.
- G-9 (row cap): alert enumeration capped at DEFAULT_ROW_CAP applied to total alerts
  collected, not per page.

### Detection signals

- MicrosoftGraphActivityLogs captures the GET /security/alerts_v2 call from the FOCI client
  ID (14d82eec), including the RequestUri (with `$filter` and `$select` projections) and
  the signing-in identity.
- **Reflexive signal** — a member-account user reading the security alert queue is anomalous
  and should trigger a Defender for Cloud Apps or Defender for Identity alert on first
  non-baseline access from that account.
- Entra ID sign-in logs: correlatable via the T1078.004 session correlation ID.

### Evidence

**R013 (2026-09-03), [samples/replay-log/R013.json](../../samples/replay-log/R013.json)** —
the W17 full sweep contains a **successful** `tool_list_security_alerts` `graph_call`
(`GET /security/alerts_v2`, 4 Defender XDR alerts, outcome success). This is Surface B's first
successful evidence: earlier R013 attempts returned HTTP 400 because the `$select` requested
`alertType` and `lastModifiedDateTime`, neither of which is a `microsoft.graph.security.alert`
property (the W17 fixes removed `alertType` and corrected `lastModifiedDateTime` →
`lastUpdateDateTime`, confirmed against the Graph v1.0 resource docs). Triaged jointly with
Surface A at `samples/finding-triage/t1654-r013-log-enumeration-001.json` (medium).

### Limitations

- `/security/alerts_v2` returns alerts from Microsoft security products integrated with
  Defender XDR (Defender for Endpoint, Defender for Identity, Defender for Cloud Apps,
  Defender for Office 365). Alerts from third-party integrations or non-Defender sources
  may not appear.
- The lab tenant may have minimal Defender product coverage, producing
  few or no alerts. The empty-result path is exercised in tests; the populated-result path
  requires at least one Defender product generating alerts in the sandbox.
- Alert `evidence` and `comments` are navigation properties not included in the `$select`
  projection; forensic evidence details are out of scope for this surface.
- Alert `incidentId` cross-linking (relating alerts to incidents) is not collected here;
  incident enumeration is a candidate for a future T1654 Surface C or a separate technique
  module.
